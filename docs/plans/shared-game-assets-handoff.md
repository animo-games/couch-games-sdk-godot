# Shared game assets: executable writer handoff

## Root-reviewed lifecycle refinement

This refinement preserves the approved public API and retains published objects. The user explicitly approved retaining shared bytes after whole-game deletion so slugs can be reused. The slice instructions below incorporate these decisions.

- Do not run automatic prefix deletion for closed games. Immutable copies that finish after game deletion stay unreachable behind the tombstone; reclaiming them is deferred with published-object garbage collection. An ownership lookup immediately before an unconditional delete is not a fence against concurrent slug reuse.
- Recover an interrupted deletion using the coordinator's existing deletion ID and journal. Persist one immutable exact deletion-manifest candidate and base precondition before any fence CAS, and permanent terminal evidence before closure. Helpers never rebase an old fence onto a reused catalog. Physical cleanup excludes the entire shared namespace; legacy cleanup retains its existing separate behavior. An authoritative stage catalog after reuse supersedes a delayed legacy tombstone for shared serving.
- Finalize operation evidence while its coordinator remains active. Persist the terminal outcome, replace the large publication attempt with a compact permanent terminal marker using CAS, and retain compact permanent intent/outcome evidence before release. A helper that cached the old attempt can issue only its exact fixed-base CAS. Helpers seeing terminal evidence validate the intent and never reconstruct or activate the operation.
- Full retry receipts have bounded retention; permanent small terminal evidence prevents an expired operation ID from becoming a new mutation. Matching expired retries return `410`; intent reuse returns `409`. Server-issued upload IDs may later return `404` after their records expire because missing records cannot reconstruct an upload.
- Do not asynchronously delete a pre-activation journal based on coordinator rechecks: deletion could race a delayed activation CAS. Retain that small evidence until it can be safely terminalized under the coordinator. Active upload records are recovered and terminalized, never expired by age alone.

This is conservative internal retention, not a new service, API, or garbage-collection policy.

## Existing slug migration: corrected exploration result

The baseline admin app already has `POST /api/games/:gameId/migrate-slug`. The initial exploration missed this route; the approved plan explicitly includes coordinating this workflow.

- Hold the game's coordinator in a resumable migration state, with a stable migration ID and canonical current slug, across the existing signed-cursor copy and SQL cutover. Reconcile active publication first; block new publication during migration and reject delayed old-slug operations after cutover.
- Exclude shared assets from the legacy unconditional copy and missed-key loops. Persist one effective manifest snapshot and exact destination publication candidate/base before copying. A present stage manifest, including an empty one, is authoritative; only absence selects production.
- Copy all retained immutable objects separately with stage precedence and conditional creation/collision checks, including superseded hashes outside the current catalog. Resolve each candidate reference by exact key from stage then production: an authoritative stage catalog can still reference inherited production bytes. Publish the exact persisted destination manifest only after its referenced objects are readable. A destination catalog, including an empty migration candidate, is reserved; only recognized retired-prefix fences are eligible for reuse.
- Reconcile the destination candidate before SQL cutover, then retain an empty migration fence at the old manifest key before releasing the coordinator bound to the new slug. Old hashed objects remain readable. Replays use the same migration ID and fixed CAS candidates, so delayed helpers cannot overwrite post-cutover edits or a reused old slug.
- Failures keep durable recovery state. Resume the existing route/cursor after interruptions on either side of SQL cutover, including a lost first response before the client receives a cursor. Bind cursorless recovery to the exact game and migration tuple. Persist permanent finalized/rejected evidence before releasing the coordinator; successful replay reads that outcome rather than comparing live catalogs that later edits or slug reuse may legitimately change. Deterministic setup rejection must leave the old game writable. Do not report success before final fencing and coordinator release.

The accompanying storage fixes must terminalize deterministic catalog-size rejection, recover expired active operations inline, release completed replays, recover active upload records, and isolate each failed coordinator during scheduled maintenance. Hono serving adapters decode raw URL paths once; invalid pagination cursors return `400`.

6. Once active, helpers must agree on one durable attempt before any manifest CAS: the winner reads and validates the target manifest (or stage absence plus the effective production snapshot), checks the expected entry state, constructs the complete deterministic candidate with the operation ID as manifest/entry revision, records the base manifest ETag or explicit absence, effective-fallback identity, candidate digest/body, and intended outcome in `staging/shared/attempts/<operationId>.json` via `If-None-Match:*`. Losing helpers read that exact attempt; they never re-read production to construct a different first-stage candidate. If expected state already mismatches, persist a conflict attempt without issuing a manifest CAS.
7. A helper may issue only the attempt's exact CAS: `If-Match:<persisted base ETag>` or `If-None-Match:*`, writing the exact persisted bytes. No helper may publish, decide conflict, or receipt before this immutable attempt exists. It waits for its issued request; a lost response remains ambiguous and forces durable reconciliation, never an independent outcome. Matching unique operation revision plus candidate digest is success; unchanged exact base is nonterminal and permits another identical CAS; a different ETag/object is the permanent invalidation that permits conflict. For an absent stage, absence is never treated as conflict: helpers keep retrying/reconciling the same `If-None-Match:*` candidate until it is present or some other object makes the precondition permanently false. Terminal receipt is derived only then, before exact-ETag active→higher-epoch idle. Thus the H1/H2 case cannot diverge: H2 uses H1's persisted fallback snapshot and exact bytes, and cannot receipt/release merely because production later changed. Two in-flight CAS calls are identical; one success changes the stage ETag and all helpers reconcile it as the same success before release. Any call already issued before release therefore either supplied that recognized candidate or failed its fixed precondition; it cannot commit a different result after a successor begins.

Exhausted 429/5xx retries or an ambiguous R2 result leave the fixed-base attempt active and recoverable; they never create a failure receipt or release the coordinator.
